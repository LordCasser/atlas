# 07-架构变动文档：提取 Tree-sitter 解析核心，分离单版本图谱与多版本源码语料库

> 本文是 Atlas 的架构变动决策文档。本文只描述新的架构边界与决策依据，不修改既有需求文档的结论。后续如需落地，应再分别更新模块契约、实施计划和对应项目文档。

---

## 1. 背景

Atlas 当前定位为一个 **local-first Rust-native 代码知识图谱引擎**：针对一个本地代码库进行扫描、解析、关系抽取、引用解析、图谱构建，并通过 MCP 为 LLM Agent 提供代码理解、调用分析、依赖分析和影响面分析能力。

近期新增了一个独立但相关的需求方向：构建一个受 Elixir 启发的 **大型多版本源码索引系统**，主要用于 Linux 这类拥有大量 release/tag 的源码项目，目标包括：

1. 高性能索引 Linux 多版本源码。
2. 使用 Git tag 和 Git blob 去重维护多个版本。
3. 提供 Elixir-compatible Web/API，方便人工浏览。
4. 提供 MCP，方便 AI Agent 在分析 bug、漏洞、回归时快速查询源码、函数实现、版本差异和引入版本。
5. 使用 Rust 实现高性能索引和查询能力。

这两个方向都需要 tree-sitter 解析、语言适配、符号抽取、引用抽取、函数范围识别等能力。但二者在数据模型、索引单位、查询模式和后端服务形态上存在根本差异。

因此，本次架构变动的核心结论是：

> **不将大型多版本源码索引能力直接并入 Atlas 主体。**  
> **而是将 Atlas 中与 tree-sitter 相关的解析核心提取为独立 Rust library crate，再由 Atlas 原项目和 Corpus 新项目分别按自身需求导入该解析库，并独立选择存储、索引、查询、Web 和 MCP 后端架构。**

---

## 2. 架构变动目标

本次变动目标不是重写 Atlas，也不是把 Atlas 改造成 Linux 专用索引器，而是通过 workspace 分层形成三个清晰边界：

```text
共享解析核心
  -> Atlas Workspace Graph：单项目、单版本、本地代码图谱
  -> Versioned Source Corpus：大型项目、多版本、源码语料库索引
```

新的目标架构应满足：

1. **解析能力复用**：tree-sitter parser、query engine、LanguageAdapter、函数/符号/引用抽取逻辑可以被多个上层产品共享。
2. **后端职责分离**：单版本项目图谱和多版本源码索引采用不同的存储模型、ID 策略、查询策略和服务接口。
3. **避免错误抽象**：不强行统一 path-based workspace graph 与 blob-based versioned corpus 的数据模型。
4. **保持 Atlas 原定位稳定**：Atlas 继续作为 local-first 单项目代码知识图谱引擎演进。
5. **允许 Corpus 独立优化**：Corpus 可以针对 Linux 等大型多版本项目选择更适合的索引结构，如 Git blob 去重、version bitmap、compressed postings、mmap segment files 等。
6. **降低许可证和产品耦合风险**：Elixir-compatible Web 前端、AGPLv3 资源复用等问题不应污染 Atlas 核心解析库和原始 Atlas 应用。

## 3. Atlas 原始项目与 Corpus 项目的需求差异

### 3.1 项目定位差异

| 维度 | Atlas 原始项目 | Corpus 新项目 |
|---|---|---|
| 产品定位 | 本地代码知识图谱引擎 | 大型多版本源码索引与查询系统 |
| 主要对象 | 当前工作区代码库 | Linux / U-Boot / BusyBox 等多版本 Git 项目 |
| 核心用户 | LLM Agent、代码审查/理解工具 | LLM Agent、漏洞分析人员、内核开发者、代码审计人员 |
| 主要问题 | 当前代码库里符号、调用、依赖、影响面是什么 | 某个版本源码是什么、函数如何实现、哪个版本引入变化、跨版本差异是什么 |
| 主要消费方式 | MCP 图谱查询 | MCP 源码/版本查询 + Elixir-compatible Web/API |

---

### 3.2 输入模型差异

| 维度 | Atlas 原始项目 | Corpus 新项目 |
|---|---|---|
| 输入来源 | 本地文件系统工作区 | bare Git repository + remotes + tags |
| 文件发现 | `git ls-files` / filesystem walk / `.atlasignore` | `git for-each-ref` + `git ls-tree -r` |
| 版本概念 | 当前工作区状态 | 大量 Git tags/releases |
| 增量基础 | 文件 mtime / git status | 新 tag、新 blob、已有 blob 复用 |
| 文件内容读取 | filesystem read | Git object read：`tag:path` 或 blob oid |

Atlas 原始项目的输入是“当前项目文件集合”；Corpus 的输入是“Git 对象数据库中的历史版本集合”。因此二者不能共享同一套文件发现和增量同步模型。

---

### 3.3 索引主键差异

| 维度 | Atlas 原始项目 | Corpus 新项目 |
|---|---|---|
| 核心索引单位 | file path | Git blob |
| 文件身份 | project root + relative path | project + git blob oid + blob_id |
| 版本文件身份 | 不需要 | tag + path -> blob_id |
| 符号身份 | file_id + local symbol | blob_id + local symbol |
| 查询过滤 | 当前项目图谱 | version bitmap / tag path map |

这是最重要的差异。

Atlas 原始项目中，`path` 是稳定且自然的文件身份；而 Corpus 中，`path` 只是某个版本视图中的路径。同一个 Git blob 可能同时出现在多个版本、多个路径中。Corpus 的稳定核心应是 Git blob，而不是路径。

因此共享解析库不应生成持久化的 path-based `FileId` / `SymbolId`，否则会对 Corpus 造成错误约束。

---

### 3.4 数据存储差异

| 维度 | Atlas 原始项目 | Corpus 新项目 |
|---|---|---|
| 推荐存储 | SQLite + GraphSnapshot | SQLite metadata + bitmap/posting/segment index |
| 数据规模 | 单项目当前版本 | 大型项目所有 release/tag 的源码集合 |
| 查询加速 | 内存 GraphSnapshot | version bitmap、symbol postings、function hash index |
| 图遍历 | callers/callees/path/impact | 版本过滤、first-seen、函数 diff、源码定位 |
| 存储目录 | project root 下 `.atlas/` | `/srv/atlas-data/<project>/` 或独立 corpus data dir |

Atlas 原始项目应继续使用 SQLite 作为 source of truth，并用 GraphSnapshot 支撑 MCP 低延迟图查询。Corpus 则需要面向大规模多版本索引设计后端，可逐步从 SQLite MVP 过渡到 roaring bitmap、compressed postings、mmap segment files 等结构。

---

### 3.5 查询模式差异

| 维度 | Atlas 原始项目 | Corpus 新项目 |
|---|---|---|
| 符号查询 | 在当前项目图谱中查 symbol | 在指定 project/version/family 中查 identifier |
| 调用查询 | callers/callees/impact/path | 函数实现、跨版本函数 diff、函数变化 timeline |
| 上下文构建 | 图谱扩展 + 代码片段 | 精确源码片段 + 版本差异 + first-seen |
| Web 浏览 | 非核心 | 核心需求，需要 Elixir-compatible UI/API |
| Agent 场景 | 理解当前代码库结构 | 分析 Linux bug/CVE、定位引入版本、比较修复差异 |

Atlas 的核心是图谱查询；Corpus 的核心是版本化源码查询。两者都需要 MCP，但 MCP tools 的语义不同。

---

## 4. 架构决策

### 4.1 决策一：采用 Cargo workspace 分层

应将当前仓库演进为 Cargo workspace，至少包含：

```text
atlas-workspace/
  Cargo.toml

  crates/
    atlas-ir/
    atlas-parse/
    atlas-lang-linux/       # 可选，后续引入

  apps/
    atlas/
    atlas-corpus/           # 可选，后续引入
```

其中：

```text
atlas-ir      存放与存储无关的通用 IR、枚举、Range、解析事实结构。
atlas-parse   存放 tree-sitter parser registry、query engine、LanguageAdapter、语言 queries。
atlas         原始 Atlas 应用，负责单项目单版本图谱。
atlas-corpus  新的多版本源码索引应用，负责 Git tag/blob 索引、Web/API、Corpus MCP。
```

---

### 4.2 决策二：解析核心只输出存储无关的事实

共享解析库的职责是：

```text
source bytes + path hint + language hint
  -> tree-sitter parse
  -> query extraction
  -> LanguageAdapter normalize
  -> ParsedFileFacts
```

共享解析库不负责：

```text
SQLite 写入
GraphSnapshot 构建
Git 操作
MCP 协议
Web/API
Elixir compatibility
跨文件 resolution
版本管理
first-seen 分析
blame/pickaxe
```

建议核心 API 形态：

```rust
pub struct ParseInput<'a> {
    pub path: &'a str,
    pub language: Option<Language>,
    pub source: &'a [u8],
}

pub struct ParseOptions {
    pub include_references: bool,
    pub include_callsites: bool,
    pub include_imports: bool,
    pub include_doc_comments: bool,
    pub best_effort: bool,
}

pub trait ParserEngine: Send + Sync {
    fn parse_file(
        &self,
        input: ParseInput<'_>,
        options: &ParseOptions,
    ) -> Result<ParsedFileFacts>;
}
```

---

### 4.3 决策三：共享解析库使用 file-local IDs，不生成持久化 IDs

解析库不应生成持久化的 `FileId` / `SymbolId` / `ReferenceId`。它只应生成局部 ID：

```rust
pub struct LocalSymbolId(pub u32);
pub struct LocalScopeId(pub u32);
pub struct LocalReferenceId(pub u32);
pub struct LocalCallsiteId(pub u32);
```

原因：

1. Atlas 原始项目和 Corpus 项目的持久化 ID 语义不同。
2. Atlas 原始项目适合基于 `project + path + local symbol` 生成 ID。
3. Corpus 适合基于 `project + blob_id + local symbol` 生成 ID。
4. 如果解析库提前生成 path-based ID，会破坏 Corpus 的 Git blob 去重模型。

上层应用负责把 local IDs 映射成自身持久化 ID：

```text
Atlas:
  project root + relative file path + LocalSymbolId
    -> SymbolId

Corpus:
  project + BlobId + LocalSymbolId
    -> BlobSymbolId
```

---

### 4.4 决策四：Atlas 原始项目继续保持单项目单版本图谱模型

Atlas 应继续负责：

```text
file discovery
.gitignore / .atlasignore
incremental sync
SQLite schema
reference resolution
GraphSnapshot
search/context
MCP graph tools
```

Atlas 的数据流保持为：

```text
scan files
  -> atlas-parse::parse_file()
  -> ParsedFileFacts
  -> assign workspace persistent IDs
  -> write .atlas/atlas.db
  -> resolve references
  -> build GraphSnapshot
  -> MCP graph query
```

Atlas 不应直接承担 Linux 多版本源码索引、Elixir-compatible Web、Git tag/blob 去重等职责。

---

### 4.5 决策五：Corpus 项目独立承担多版本源码索引模型

Corpus 项目应独立负责：

```text
Git bare repo 管理
remote/tag sync
Git blob 去重
tag -> path -> blob 映射
version bitmap
symbol/ref/function index
Elixir-compatible Web/API
Corpus MCP tools
first-seen / diff / blame / pickaxe 查询
```

Corpus 的数据流应为：

```text
fetch remotes
  -> list tags
  -> git ls-tree per tag
  -> blob dedup
  -> parse only new blobs via atlas-parse
  -> assign corpus persistent IDs
  -> write corpus backend
  -> build version bitmap / postings
  -> serve Web/API/MCP
```

Corpus 可根据自身性能需求选择后端：

```text
MVP:
  SQLite metadata + basic indexes + roaring bitmap

后续:
  compressed postings
  mmap segment files
  function hash index
  query cache
```

---

### 4.6 决策六：Linux 特化解析规则不进入通用解析核心

Linux Corpus 需要一些 Elixir-inspired 或 Linux-specific 规则，例如：

```text
SYSCALL_DEFINE*
ENTRY(...)
SYM_FUNC_START(...)
EXPORT_SYMBOL(...)
MODULE_*
Kconfig CONFIG_*
Makefile CONFIG_*
DTS compatible
Devicetree binding docs
```

这些规则不应直接污染通用 `atlas-parse`。建议后续独立为：

```text
crates/atlas-lang-linux
```

由 Corpus 选择性导入。这样可以保持：

```text
atlas-ir / atlas-parse     通用、MIT-friendly、面向多语言解析
atlas-lang-linux           Linux-specific extension
atlas-corpus               多版本 Linux/source corpus 应用
```

---

### 4.7 决策七：跨文件 resolution 不放入解析库

解析库只抽取源码事实，不解析跨文件关系。

例如解析库可以输出：

```text
这里有一个 call expression，名字是 foo
这里有一个 include，文本是 linux/sched.h
这里有一个 import，模块名是 x.y.z
```

但不负责判断：

```text
foo 最终指向哪个函数
include 最终对应哪个文件
import 最终解析成哪个 package symbol
```

原因是 Atlas 与 Corpus 的 resolution 上下文不同：

```text
Atlas:
  当前工作区文件集合 + 当前 SQLite symbols/references

Corpus:
  指定 version/tag 的 path/blob 集合 + version-aware symbol index
```

跨文件解析应分别由上层应用实现。

## 7. ID 策略

### 7.1 解析库局部 ID

解析库只保证一个文件解析结果内部的引用一致性：

```text
ParsedSymbol.local_id
ParsedReference.source_symbol
ParsedCallsite.reference_id
ParsedScope.parent
```

这些 ID 不跨文件、不跨版本、不持久化。

---

### 7.2 Atlas 持久化 ID

Atlas 可以继续使用面向工作区的 ID 策略：

```text
FileId       = hash(project_root + relative_path)
SymbolId     = hash(file_id + symbol_path/name/range)
ReferenceId  = hash(file_id + local_reference + range)
CallsiteId   = hash(file_id + local_callsite + range)
```

该策略服务于当前工作区图谱。

---

### 7.3 Corpus 持久化 ID

Corpus 应采用 blob/version-aware ID：

```text
BlobId          = assigned integer or hash(project + git_blob_oid)
VersionFileId   = hash(project + tag + path)
BlobSymbolId    = hash(project + blob_id + local_symbol_id/range/name)
BlobReferenceId = hash(project + blob_id + local_reference_id/range/name)
FunctionBodyId  = hash(project + blob_id + function range/body hash)
```

这样可以支持：

```text
同一个 blob 跨多个版本复用解析结果
同一个 tag 下 path -> blob 映射
按 version bitmap 过滤 symbol/ref/function postings
```

## 8. 数据流对比

### 8.1 Atlas 数据流

```text
scan workspace files
  -> read filesystem file
  -> atlas-parse parse
  -> ParsedFileFacts
  -> workspace ID mapping
  -> SQLite write
  -> workspace resolution
  -> GraphSnapshot refresh
  -> MCP graph/search/context query
```

---

### 8.2 Corpus 数据流

```text
fetch Git remotes
  -> list tags
  -> enumerate tree for each tag
  -> get/create blob_id by git oid
  -> write tag/path/blob mapping
  -> enqueue new blobs only
  -> read blob content
  -> atlas-parse parse
  -> corpus ID mapping
  -> write symbol/ref/function indexes
  -> build version bitmap
  -> serve Elixir-compatible Web/API and Corpus MCP tools
```

## 9. 非目标

本次架构变动明确不做：

```text
1. 不把 Linux Corpus 直接并入 Atlas 原始应用主体。
2. 不强行统一 Atlas workspace graph schema 和 Corpus schema。
3. 不让解析库依赖 SQLite、Git、MCP 或 Web。
4. 不让解析库生成持久化 path-based ID。
5. 不在通用解析库中内置 Linux-specific 规则。
6. 不要求 Corpus 使用 Atlas 当前 GraphSnapshot。
7. 不要求 Atlas 原始项目支持多版本 Git tag/blob 索引。
8. 不在本阶段决定 Elixir 前端资源是否直接复用。
```

## 10. 许可证边界说明

Atlas 当前项目许可证为 MIT。Elixir 项目为 AGPLv3。

本次架构变动将解析核心独立出来，有助于保持以下边界清晰：

```text
atlas-ir / atlas-parse:
  通用解析库，原则上保持 MIT。

apps/atlas:
  原始 Atlas 应用，原则上保持 MIT。

apps/atlas-corpus:
  多版本源码索引应用。
  如果直接复用 Elixir 前端模板、CSS、JS、图标等资源，需要单独评估 AGPLv3 影响。
```

建议 Corpus MVP 优先实现 Elixir-compatible API/URL，而不是直接复制 Elixir 前端资源。前端视觉和资源复用应作为单独许可证决策处理。

3. 保证现有测试和 CLI 可运行。

## 12. 验收标准

本次架构变动的验收标准不是功能全部完成，而是边界清晰、解析核心可复用：

1. `atlas-ir` 不依赖任何后端存储或服务框架。
2. `atlas-parse` 可以在没有 SQLite、MCP、Git 的情况下独立解析源码并输出事实。
3. Atlas 原始应用通过 `atlas-parse` 获得解析结果，再自行生成持久化 ID 并写入现有后端。
4. Corpus 原型可以读取一个 Git blob 内容，调用 `atlas-parse` 获得解析结果，并自行映射为 blob-based ID。
5. Atlas 原始项目和 Corpus 项目可以独立选择存储和查询架构。
6. Linux-specific 解析规则有独立扩展位置，不污染通用解析核心。

---

## 13. 最终结论

本次架构变动确立以下长期方向：

> **Atlas 不再只是单个应用，而应演进为一个包含共享解析核心和多个上层产品的 Rust workspace。**

其中：

```text
atlas-ir / atlas-parse
  是通用、存储无关、面向 tree-sitter 的解析事实抽取核心。

apps/atlas
  是单项目、单版本、本地代码知识图谱应用。

apps/atlas-corpus
  是大型项目、多版本、Git blob 去重的源码语料库索引应用。
```

这种分层能够同时满足：

1. Atlas 原始项目继续稳定演进。
2. Linux/Elixir-inspired Corpus 项目独立采用更适合大型多版本源码的后端架构。
3. tree-sitter 语言解析能力在两个项目间长期共享。
4. 避免单一后端同时承担两种本质不同的数据模型。
5. 为未来更多上层产品复用解析核心提供清晰基础。
